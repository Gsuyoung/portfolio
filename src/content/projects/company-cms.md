## 프로젝트 소개

재직 중인 회사에서 진행한 고객사 프로젝트입니다. 사용자에게 보이는 **기업 소개 홈페이지**와, 문의 · 배너 · 뉴스 · 약관을 관리하는 **관리자 페이지**의 백엔드를 맡았습니다. 백엔드 개발자는 저 혼자였고, 프론트엔드 개발자 1명과 API를 맞춰 가며 진행했습니다.

회사 프로젝트라서 소스 코드와 고객사 정보는 공개하지 않습니다. 대신 **무엇을 맡았고 어떤 문제를 어떻게 판단해 풀었는지**를 정리했습니다.

## 담당 업무

**설계**

- 와이어프레임을 기준으로 ERD를 설계하고 API 명세서를 작성했습니다.
- 관리자 대시보드의 방문자 집계를 고려해 방문 기록 테이블을 추가했습니다.

**프로젝트 기반**

- 초기 설정, 암 · 복호화 공통 모듈(AES-GCM), 운영 환경을 포함한 환경별 설정 파일 분리
- ArchUnit 테스트로 계층 규칙 강제 (Controller의 Repository 직접 의존 · 필드 주입 · 잘못된 위치의 `@Transactional` 금지)
- 운영 서버 구성: Spring Boot JAR 배포, Nginx 라우팅, HTTPS 적용

**도메인 API (설계 → 구현)**

| 도메인 | 기능 |
| --- | --- |
| 관리자 인증 | 로그인 · 로그아웃 · Access Token 재발급 · 관리자 정보 조회 |
| 대시보드 | 방문자 현황, 문의 집계, 최근 문의, 뉴스 현황 |
| 문의 | 등록 · 답변 등록(답변 메일 발송) · 목록 · 상세 · 응답 여부 변경 |
| 배너 | 등록 · 수정 · 이미지 변경 · 삭제 · 노출 배너 조회 |
| 뉴스 | 등록 · 수정 · 썸네일 변경 · 삭제 · 공개 목록 |
| 약관 | 정책 수정 · 조회 |
| 방문 기록 | 방문자 키 발급, 같은 날 재방문은 중복 저장하지 않음 |

**프론트엔드 연동 대응**

- 문의 유형 확장(3종 → 5종), 뉴스 게시일 타입 변경(날짜 → 날짜 + 시간)
- 배너를 다중 링크 구조로 변경, 화면별 목록 크기 파라미터 추가
- 주간 방문자 집계 기준을 "최근 7일"에서 "월 ~ 일"로 변경

**문서**

- Swagger를 관리자 API와 사용자 API로 나눠 조회할 수 있도록 정리했습니다.

## 기술적으로 고민한 점

### 세션 단위로 리프레시 토큰 관리하기

```text
[수정 전]  로그인 ─▶ Redis Key = 관리자 ID (고정)
           재로그인 ─▶ 같은 Key에 새 값 저장 ─▶ 로그아웃했던 이전 쿠키도 다시 통과

[수정 후]  로그인 ─▶ Session ID(UUID) 새로 발급 ─▶ Redis Key · 쿠키 식별값으로 사용
           로그아웃 ─▶ 해당 Session ID 데이터만 삭제 ─▶ 이전 쿠키는 더 이상 유효하지 않음
```

### 저장할 때와 보여 줄 때 모두 막는 XSS 방어

```text
관리자 에디터 입력(HTML)
   │
   ├─▶ jsoup Sanitizer : 위험한 태그 · 속성 정리 ─▶ 저장
   └─▶ 빈 값 · 글자 수 검증 : 태그를 뺀 표시 텍스트 기준 (제목 100 / 문구 500)

화면 출력 ─▶ 프론트엔드에서도 허용 태그만 렌더링
```

### 암호화 방식 변경 (AES → AES-GCM)

기존에 쓰던 `AesBytesEncryptor`가 현재 사용 중인 Spring Security 버전에서 지원되지 않아, `AesGcmBytesEncryptor`(GCM 모드)로 바꾸고 암 · 복호화 공통 모듈로 구성했습니다. 암호화에 더해 인증 태그로 데이터가 바뀌지 않았는지(무결성)도 함께 검증할 수 있게 되었습니다.

### 화면에 정의되지 않은 요구사항 판단하기

- **배너 노출**: 관리자 화면에 배너 목록이 없어 단일 노출 구조로 판단하고, 동시 노출을 최대 1개로 제한하며 중복 노출을 검증했습니다.
- **뉴스 등록**: 신규 등록 화면이 없어 썸네일을 별도로 등록하는 방식으로 구현했습니다.
- 두 경우 모두 판단 근거를 티켓에 남기고, 디자인팀과 협의해 바꿀 수 있도록 공유했습니다.

### 인증 실패도 같은 형식으로 응답하기

JWT 검증은 Spring Security 필터에서 일어나는데, 필터는 컨트롤러보다 앞단에서 동작해 여기서 난 예외는 `@RestControllerAdvice`로 잡히지 않았습니다.

```text
JwtFilter : 만료 · 위변조 등 예외 종류를 요청에 기록
   │
   └─▶ 인증 실패 처리기 : 기록을 읽어 공통 예외 처리로 넘김 ─▶ 회사 공통 응답 형식으로 응답
```

프론트는 토큰 만료면 재발급, 위변조면 재로그인으로 나눠 대응할 수 있고, 회사 공통 형식이라 다른 프로젝트에서도 그대로 재사용할 수 있습니다.

### 약관 동의 시점의 내용 보존

문의할 때 고객이 동의하는 대상은 세부 약관 4개입니다. 관리자가 나중에 약관을 고치면 과거 문의자가 어떤 내용에 동의했는지 알 수 없게 되므로, **문의 시점의 약관 전문을 이어 붙여 문의 데이터에 스냅샷으로 저장**했습니다. 약관이 모두 준비되지 않은 상태에서는 문의 등록을 막았습니다.

### 로그인 없는 사이트의 방문자 집계

```text
첫 방문 ─▶ visitorKey 없음 ─▶ 서버가 UUID 발급 ─▶ 프론트가 보관
재방문   ─▶ 같은 키로 기록 요청 ─▶ 오늘 같은 키의 기록이 있으면 저장 생략
           (visitor_key, visit_date) unique 제약으로 하루 1회만 집계
```

대시보드 요구사항에 맞춰 주간 집계를 "이번 주(월 ~ 일) / 지난주" 기준으로 바꾸고, 지난주 방문자가 0명일 때 증감률 계산의 0 나누기도 막았습니다. 월간 집계와 기간 검색은 끝을 "말일 23:59:59"로 잡지 않고 "다음 달 1일 0시 미만"(검색은 "종료일 다음 날 0시 미만")으로 조회해, 밀리초 단위 데이터가 빠지지 않게 했습니다.

## 운영 서버 구성 중 만난 문제

운영 서버를 직접 구성하면서 애플리케이션 코드 밖의 문제를 처음 다뤄 봤습니다. Nginx 설정 검사(`nginx -t`, 적용될 전체 설정 출력 `nginx -T`), access / error 로그, Spring Boot 로그를 차례로 보며 요청이 어디까지 갔는지 추적했습니다.

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| POST 요청 405 | Nginx는 `/api/` 요청만 Spring Boot로 넘기고 나머지는 정적 파일로 처리하는데, 프론트가 회사의 기존 API 경로 접두어를 붙이지 않아 POST 요청이 정적 파일 처리로 들어감. 정적 파일은 POST를 받지 않아 405 발생 | 프론트에 경로 규칙을 맞춰 달라고 요청 → 프론트 재배포 |
| 403 접근 오류 | Nginx 설정의 root 경로를 잘못 지정 | 올바른 경로로 다시 지정 |
