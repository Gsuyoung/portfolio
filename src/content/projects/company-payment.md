## 프로젝트 소개

재직 중인 회사에서 진행한 결제 연동 프로젝트입니다. 매장 POS 화면에서 결제를 요청하면, 매장 PC에 설치된 **VAN사 결제 단말 프로그램**과 통신해 카드 **승인 · 취소 · 거래 중지**를 처리합니다. 처음 다뤄 보는 결제 규격이라 VAN사가 공개한 연동 매뉴얼을 분석하고, AI 코딩 도구를 함께 활용해 구현했습니다. 내 PC에 실제 단말기를 연결해 테스트 모드로 승인 · 취소 · 거래 중지를 모두 확인했습니다.

회사 프로젝트이고 VAN사 규격 문서를 바탕으로 만든 모듈이라, 소스 코드와 통신 규격(전문), 단말기 정보, 보안 구성은 공개하지 않습니다.

```text
매장 PC
  POS 화면 ──REST──▶ 결제 연동 서버 ──WebSocket──▶ VAN사 결제 단말 프로그램 ──▶ 카드 리더기
                                                          │
                                                          └──▶ VAN사 · 카드사 승인
```

- 카드번호는 결제 연동 서버를 거치지 않습니다. 카드 입력은 결제 단말 프로그램과 리더기가 처리하고, 응답에는 마스킹된 카드번호만 담깁니다.

## 구조가 바뀐 과정

처음에는 결제 시스템이 VAN사 결제 단말 프로그램과 연동하는 구조라는 것을 몰라, 직접 결제 서버를 설계했습니다. 시험용 단말기를 어떻게 연결하는지 의문이 생겨 팀장님께 확인했고, 실행 프로그램 방식 매뉴얼에 집중해 흐름을 다시 잡았습니다. 연동 방식을 이해한 뒤에는 처음 만든 버전을 남겨 두고, 실제 구조에 맞춰 새로 만들었습니다.

```text
처음  직접 설계한 중앙 결제 서버         DB · Redis 락 · 인증 · 사업자 / 단말기 관리 포함
        │  단말기 연결 방식 의문 → 실행 프로그램 방식 매뉴얼 분석 → 결제 단말 프로그램과 연동하는 구조임을 확인
이후  매장 PC 로컬 결제 연동 서버 (새로 구성)   승인 · 취소 · 중지에 집중
```

## 결제에서 가장 먼저 정한 원칙

결제 연동에서 가장 큰 사고는 **이중 결제**입니다. 통신이 끊긴 거래를 "거절"로 표시하면 손님은 카드를 다시 긁는데, 실제로 첫 승인이 났다면 돈이 두 번 나갑니다.

```text
응답이 돌아옴 + 승인 코드          ─▶ 승인
응답이 돌아옴 + 승인 아닌 코드     ─▶ 거절      승인되지 않은 것이 확실 → 다시 결제해도 안전
통신 실패 · 시간 초과 · 응답 없음  ─▶ 결과 모름  승인 여부를 알 수 없음 → 거절로 단정하지 않음
```

- **거절과 결과 모름을 분리**해, 결과를 모르는 거래는 바로 다시 결제하지 않고 POS가 확인 절차를 거치도록 했습니다.
- 매장 리더기는 1대라서 **결제가 진행 중이면 다음 요청을 기다리게 하지 않고 바로 거절**했습니다. 요청을 쌓아 두면 손님이 떠난 뒤에 리더기가 카드를 요구할 수 있기 때문입니다.
- 거래 중지는 진행 중인 결제를 멈추는 기능이라 잠금을 잡지 않고, 매뉴얼에 안내된 중지 전용 연결로 보냈습니다. 중지를 요청했어도 실제로 승인이 난 거래는 승인으로 응답합니다.
