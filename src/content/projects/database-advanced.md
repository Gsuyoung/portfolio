## 프로젝트 개요

**나의 작은 탕비실**은 사무실에서 반복적으로 쓰는 탕비용품 · 소모품을 간편하게 주문하고 사무실로 바로 배송받는 **기업 전용 쇼핑 플랫폼**입니다. 다양한 브랜드 제품을 비교하고 비품을 손쉽게 관리하는 환경을 목표로 기획했습니다.

애플리케이션 코드가 아닌 **DB 중심 프로젝트**라서, 화면 구현보다 데이터 모델링, 트리거 · 프로시저 설계, 쿼리 검증에 집중했습니다.

```text
마인드맵  →  요구사항 명세서  →  ERD  →  쿼리 성능 테스트
```

- **프로젝트 목표**: 운영 효율화 · 고객 만족도 향상 · 정확한 재고와 정산 관리

## 담당 영역 — 구매 · 배송 데이터 설계

팀원들과 함께 **전체 ERD 설계에 참여**했고, 개인적으로는 **상품 구매부터 배송까지의 흐름**과 **교환 · 환불 테이블 설계**를 맡았습니다. 교환 · 환불은 테이블 설계까지 담당했고, 관련 시나리오 쿼리는 CS 담당 팀원이 진행했습니다.

- 구매(`purchase`) → 구매 상품(`purchase_item`) → 출고 → 송장(`delivery_number`) → 배송 물품(`delivery_item`)으로 이어지는 구조를 설계했습니다.
- 구매 건을 기준으로 이어지는 교환 · 환불 테이블과 참조 관계를 설계했습니다.
- 재고 · 출고 담당 팀원과 맞닿는 지점을 협의해 ERD에 반영했습니다.

### 구매 · 배송 트리거

상품별 처리 상태가 바뀔 때 후속 데이터가 빠짐없이 따라오도록 트리거를 만들었습니다.

- **출고 상태 갱신 · 송장 등록**: 구매 목록 안의 상품별 상태가 바뀌면 주문 전체의 출고 상태를 바꾸고, 송장 번호 테이블에 행을 추가합니다. 일부 상품만 먼저 나가는 **부분 출고**를 고려했습니다.
- **배송 물품 등록**: 상품 처리 상태에 따라 배송 물품 테이블에 행을 추가합니다.

## 조회 성능 개선 — 날짜 · 지역별 배송 상태

테스트 주제는 **날짜별 · 지역별 배송 상태 조회**(예: 2025-05-19, 대구 수성구)였습니다. 테이블 8개를 조인해 558건을 돌려주는 조회를 세 가지 방식으로 작성하고 실행 계획을 비교했습니다.

```text
테스트 데이터
  purchase_item     510,444행     purchase          169,816행
  user              108,399행     delivery_number    88,627행
  customer_address   54,111행     product_detail     31,652행
  delivery_item      22,159행     product            10,983행

단계   쿼리 방식              실행 계획                                  응답
────   ─────────────────     ──────────────────────────────────────    ──────
v1     JOIN 단순 조회         Table scan + Filter, 54,111행 스캔          710ms
                             (customer_address 전체 스캔)
v2     FULLTEXT + MATCH       Index lookup + Filter, 22,159 loops         473ms
                             (대부분 인덱스 사용)
v3     MATCH + 서브쿼리        Index lookup + Filter, 22,159 loops         231ms
                             (전부 인덱스 + 커버링 인덱스)
```

- 주소 검색에 FULLTEXT 인덱스를 추가하고 `MATCH ... AGAINST`로 바꿔, `customer_address`를 전부 읽던 구간을 인덱스 조회로 바꿨습니다.
- 서브쿼리로 조회 범위를 먼저 좁혀, 필요한 컬럼을 인덱스만으로 읽는 **커버링 인덱스**가 되도록 했습니다.
- 응답 시간은 **710ms → 231ms로 약 67% 줄었습니다.**

가장 큰 테이블이 약 51만 건이라 체감 차이는 크지 않았습니다. 그래도 실행 계획이 전체 스캔에서 커버링 인덱스로 바뀌는 과정을 직접 확인한 것이 이 프로젝트에서 얻은 가장 큰 경험입니다.

## 팀 전체 설계에서 고려한 업무 흐름

아래는 팀 전체의 설계를 요약한 것으로, 개인 담당은 구매 · 배송입니다.

- **고객 · 혜택**: 유저 공통코드, 멤버십 가입과 자동 갱신(이벤트 스케줄러), 쿠폰 최소 주문 금액 확인
- **재고 · 입출고**: 출고 확정 시 재고 차감과 임계치 확인, 부족분 입고 등록
- **CS**: 교환 · 환불 · 회수 흐름과 배송 문제 · 회수 실패 조회
- **업체 정산**: 판매 · 환불 · 교환 · 회수 배송비 정산 레코드 생성과 반영
